Esta seccion establece el esquema de organizacion y control de versiones aplicado para el seguimiento de modificaciones del proyecto Ya Quedo, usando GitHub como plataforma principal.

## GitFlow workflow

Tomando como referencia el articulo *"A successful Git branching model"* de Vincent Driessen, se aplica una version simplificada de GitFlow:

### Ramas permanentes

| Rama | Proposito |
|---|---|
| `main` | Codigo de produccion, refleja el estado de los servicios desplegados (Railway + Vercel + GitHub Pages). Solo recibe merges desde `develop` cuando se publica un release con tag formal Semver |
| `develop` | Integracion de features completadas. Es la rama "viva" del equipo durante el sprint. PRs de features merge aqui |

### Ramas temporales y convenciones de nombramiento

| Tipo | Patron | Ejemplo |
|---|---|---|
| **Feature branch** | `feature/us-<NN>-<NN>-<modulo>-<owner>` o `feature/<sprint>-<tema>-<owner>` | `feature/us-01-02-auth-jose`, `feature/tb3-frontend-yago` |
| **Release branch** | `release/v<MAJOR>.<MINOR>.<PATCH>` (cuando hay multiples PRs preparando un release) | `release/v1.0.0` |
| **Hotfix branch** | `hotfix/<descripcion-corta>` | `hotfix/jwt-token-expiration` |
| **Chore / docs** | `chore/<descripcion>` o `docs/<seccion>` | `chore/tb3-cleanup-and-deploy`, `docs/tb3-informe-secciones-faltantes` |
| **Fix sin US** | `fix/<descripcion>` | `fix/seed-bcrypt-hashes` |

### Flujo tipico de una feature

1. `git checkout develop && git pull --ff-only origin develop`
2. `git checkout -b feature/us-03-05-worker-yago`
3. Implementar + commit con Conventional Commits
4. `git push -u origin feature/us-03-05-worker-yago`
5. `gh pr create --base develop --head feature/...` (Pull Request)
6. Revisor humano aprueba
7. `gh pr merge --squash --delete-branch` (squash + cleanup)
8. La feature branch queda eliminada en remoto

### Flujo de release

1. Cuando `develop` tiene todas las features del sprint mergeadas: `gh pr create --base main --head develop --title "release: v1.0.0"`
2. Merge a `main` con merge commit (no squash, preserva historia)
3. `git tag -a v1.0.0 -m "<release notes>"` desde `main`
4. `git push origin v1.0.0`
5. `gh release create v1.0.0 --notes "..."` para publicar la nota visible en GitHub
6. Railway y Vercel detectan el push a `main` y redeploy automatico

## Semantic Versioning 2.0.0

Las versiones siguen `MAJOR.MINOR.PATCH` segun **Semantic Versioning 2.0.0**:

- **MAJOR**: cambios incompatibles en la API publica (ej. eliminar endpoint, cambiar contrato JSON)
- **MINOR**: nueva funcionalidad backward-compatible
- **PATCH**: correcciones backward-compatible

| Version | Fecha | Hito |
|---|---|---|
| `v0.1.0` | 2026-04-21 | Sprint 1: Landing Page publicada |
| `v0.5.0` | 2026-05-15 | Sprint 2: backend con 32 endpoints + 11 US |
| **`v1.0.0`** | **2026-06-12** | **Sprint 3 / TB3: end-to-end con frontend + tests + F03 Mi perfil** |
| `v1.1.0` (futuro) | TP Sem 14 | Sprint 4: IA Assistant + pagos sandbox + edicion perfil trabajador |

## Conventional Commits

Todos los commits siguen el estandar de **Conventional Commits** para auto-generar changelog y dejar historial auditable.

### Estructura

```
<tipo>(<modulo opcional>): <descripcion breve en presente>

[cuerpo opcional con explicacion en mas detalle, separado por linea en blanco]

[footer opcional, ej. BREAKING CHANGE: ..., Closes #X]
```

### Tipos usados en el proyecto

| Tipo | Cuando |
|---|---|
| `feat` | Nueva funcionalidad visible al usuario |
| `fix` | Bug fix |
| `chore` | Mantenimiento que no agrega ni quita funcionalidad (ej. limpieza, configs) |
| `docs` | Cambios solo en documentacion |
| `test` | Agregar o ajustar tests |
| `refactor` | Reorganizacion de codigo sin cambios funcionales |
| `style` | Formateo, sin impacto en logica |
| `perf` | Mejora de performance |

### Ejemplos del proyecto

- `feat(auth): JWT login + register con BCrypt strength 12`
- `fix(deploy): V4 fix BCrypt seed + apunta frontend Vercel al backend Railway`
- `chore(tb3): cleanup repo + deploy configs alineados al patron del profe`
- `docs(informe): agrega 5.2.3.1 Sprint Planning III + 5.2.3.6 Team Collaboration`
- `test(worker): cobertura completa de TrabajadorService (9 tests)`
