# 5.1.4. Source Code Style Guide & Coding Conventions

El equipo TetraDev adopta las siguientes guias y convenciones para nombrar elementos y programar en los lenguajes utilizados en la solucion. **Toda la nomenclatura es en ingles** salvo excepciones documentadas (el dominio de negocio permite terminos en espanol en clases de tipo entidad/DTO porque facilitan la traza con la jerga de los stakeholders peruanos: cliente, trabajador, solicitud, resena).

## HTML

Basado en *HTML Style Guide and Coding Conventions* y *Google HTML/CSS Style Guide*.

- Lowercase para nombres de elementos y atributos: `<input type="email">` no `<INPUT TYPE="EMAIL">`
- Indentacion: 2 espacios, sin tabs
- Cerrar siempre etiquetas opcionales (`</li>`, `</p>`)
- Valores de atributos entre comillas dobles
- `lang="es-419"` en `<html>` (espanol Latam)
- Atributos ARIA en elementos interactivos: `aria-label`, `aria-controls`, `role`
- Encabezados semanticos `<h1>` solo uno por documento
- Imagenes con `alt` siempre

Ejemplo del Landing Page (`index.html`):
```html
<button class="cta cta--primary" type="button" aria-label="Pre-registrarme como cliente">
  Quiero un tecnico
</button>
```

## CSS

Basado en *Google HTML/CSS Style Guide*.

- BEM (Block Element Modifier) para nombres de clases: `.card`, `.card__title`, `.card--featured`
- Variables CSS para tokens del Design System: `--color-primary`, `--spacing-md`, `--radius-lg`
- Mobile-first con media queries `@media (min-width: 768px)`
- Shorthand cuando aplica (`margin: 8px 16px` no `margin-top: 8px; margin-right: 16px`)
- 0 sin unidad (`margin: 0` no `margin: 0px`)
- Lowercase hex colors (`#3f51b5`)

## JavaScript (Landing)

Basado en estandares ECMAScript modernos.

- `const` por default, `let` solo si reasignacion, **nunca** `var`
- Arrow functions para callbacks
- `===` siempre, nunca `==`
- camelCase para variables y funciones: `getUserProfile`, `formSubmitHandler`
- PascalCase para clases: `LanguageSwitcher`, `FormValidator`
- Modules ES6 (`import` / `export`)
- Sin `console.log` en codigo final (eliminados antes del commit)

## TypeScript (Frontend Angular)

Basado en *Google TypeScript Style Guide* y *Angular coding style guide*.

- **camelCase** para variables, propiedades, metodos
- **PascalCase** para clases, interfaces, types, enums: `AuthService`, `TrabajadorResponse`, `UserRole`
- **kebab-case** para nombres de archivos: `mi-perfil.component.ts`, `auth.interceptor.ts`
- **Sufijos** de Angular obligatorios: `.component.ts`, `.service.ts`, `.guard.ts`, `.interceptor.ts`, `.model.ts`, `.pipe.ts`
- Standalone components (sin NgModules)
- Imports ordenados: Angular core → terceros → app
- Lifecycle hooks como metodos publicos: `ngOnInit()`, `ngOnDestroy()`
- Subscriptions liberadas con `takeUntilDestroyed()` o `async` pipe
- Signals para estado reactivo local (`signal()`, `computed()`)
- ReactiveForms tipados con `FormGroup<{...}>` o `nonNullable.group({})`
- No `any` salvo en boundary explicito (ej. respuestas dinamicas del backend)

Estructura del Web App siguiendo *Angular coding style guide*:
```
src/app/
├── core/              # singletons (services, guards, interceptors)
│   ├── guards/
│   ├── interceptors/
│   ├── models/
│   └── services/
├── features/          # feature modules (uno por dominio)
│   ├── auth/
│   ├── workers/
│   ├── requests/
│   ├── reviews/
│   └── perfil/
└── shared/            # reusable UI (layout, pipes, validators)
    └── layout/
```

## Java (Backend Spring Boot)

Basado en *Google Java Style Guide* y *Spring Boot Features*.

- Indentacion: 4 espacios
- **PascalCase** para clases, interfaces, enums: `TrabajadorService`, `ITrabajadorService`, `EstadoSolicitud`
- **camelCase** para metodos y variables: `findById`, `nuevoPromedio`
- **UPPER_SNAKE_CASE** para constantes: `DEFAULT_PAGE_SIZE`, `JWT_HEADER_NAME`
- **lowercase** dot-separated para paquetes: `com.tetradev.yaquedo.worker.service`
- DTOs como **records** (Java 17+): `public record CreateTrabajadorRequest(...)`
- Validacion declarativa con `jakarta.validation`: `@NotBlank`, `@Pattern`, `@Email`
- Entities con `@Entity` + `@Table(name="...")` + getters/setters via Lombok `@Getter @Setter`
- Mappers MapStruct con `@Mapper(componentModel = "spring")`
- Servicios con `@Service` + `@RequiredArgsConstructor` (constructor injection via Lombok)
- Repositories extienden `JpaRepository<Entity, UUID>`
- Controllers con `@RestController` + `@RequestMapping("/api/...")` + `@Tag` para Swagger
- Excepciones del dominio: clases dedicadas (`TrabajadorYaExisteException`, `ResourceNotFoundException`) + handler global `@RestControllerAdvice`

Estructura del backend siguiendo arquitectura por capas dentro de cada modulo:
```
com.tetradev.yaquedo.<modulo>/
├── controller/
├── service/
│   ├── I<Modulo>Service.java       (interface)
│   └── <Modulo>Service.java        (implementacion)
├── repository/
├── mapper/
├── dto/
├── exception/
└── model/                          (JPA entities)
```

## Gherkin (criterios de aceptacion de User Stories)

Basado en *Gherkin Conventions for Readable Specifications*.

```gherkin
Funcionalidad: F02 Inicio de sesion y autenticacion

Escenario: Cliente con credenciales validas accede al sistema
  Dado que existe un usuario "ana@yaquedo.pe" con password "password123"
  Cuando hago POST a /api/auth/login con esas credenciales
  Entonces recibo HTTP 200 con un accessToken JWT firmado
  Y el JWT contiene el rol "CLIENTE" en el claim "role"

Escenario: Credenciales invalidas son rechazadas
  Dado que existe un usuario "ana@yaquedo.pe" con password "password123"
  Cuando hago POST a /api/auth/login con password "wrong"
  Entonces recibo HTTP 401 con mensaje "credenciales invalidas"
```
